<p>同一个出口上如果同时跑着二十个互不相干的账号，出口本身就会变成一条公共走廊；再叠加前手留下的访问记录和过于频繁的换手节奏，被标记就不再是单点问题，而是一串因素叠加的结果。下面把它拆成三种不同的事，各自给一条判断路径，最后落到五个可以自己动手的检查点。</p>

<h2>一、先把被标记拆成三种不同的事</h2>
<p>「被标记」是个笼统说法，三种情况的现象、影响范围和处理方式完全不同，混着看只会越查越乱。</p>
<h3>出口侧的整体降级</h3>
<p>表现为这条线路上的多个账号同时出现异常，换账号不变、换线路就好。问题在资源侧，与单个账号无关，处理方式是换出口而不是改账号。</p>
<h3>账号侧的关联</h3>
<p>表现为某几个账号同时受限，其他账号在同一出口上正常。问题在账号之间有没有共用设备、共用操作习惯，出口只是被牵连。</p>
<h3>单次会话的风控</h3>
<p>只影响一次请求或一个短时段，重试或稍等即可恢复。这类多数由瞬时请求特征触发，不必上升到换资源的层面。</p>

<h2>二、分支一：共享率过高，出口变成公共走廊</h2>
<p>共享本身不是问题，共享到什么程度才是问题。一条出口服务三个账号和三十个账号，风险量级完全不同。</p>
<h3>共享率怎么估</h3>
<p>看三个数：单 IP 的同时在线账号数、日请求总量、以及换手频率。前两个可以问供应商，第三个只能靠自己的观察和工单记录推断。</p>
<h3>什么密度算偏高</h3>
<p>经验上，一条住宅出口同时承载超过 5 个活跃账号，行为特征就开始变得不像家庭用户；超过 10 个，任何异常都会被放大到整条线路。这个数字不是标准，只是参考起点。</p>

<h2>三、分支二：历史记录，前手留下的痕迹</h2>
<p>新买的线路未必是「干净」的。它在到你手上之前可能已经被用过一段时间，这段历史你无法清除。</p>
<h3>能查到的部分</h3>
<p>用公开查询入口看归属与 ASN 是否正常，用回显接口确认地址与标注地区一致，用常见端口做连通性测试。三项都正常，说明基础状态没问题，但不代表历史干净。</p>
<h3>查不到的部分怎么问</h3>
<p>直接问供应商：这条 IP 的分配时长、上一个使用方的行业类型、是否做过高频请求。愿意给出口径的，通常管理更规范；含糊其辞的，把风险计入价格。</p>

<h2>四、分支三：复用节奏，换手太快也是问题</h2>
<p>频繁更换出口，看起来是在「规避风险」，实际上是在制造新的不一致。</p>
<h3>换手频率</h3>
<p>同一账号在一周内跨三条以上出口，登录地、时区、网络特征全部变化，这种模式本身就与正常用户不符。建议同一账号的出口变更控制在每月一次以内。</p>
<h3>冷却期</h3>
<p>从一条出口撤下后，不要立刻给另一个账号使用。留三到七天的冷却期，让这段时间的自然流量把使用痕迹冲淡一些，成本几乎为零。</p>

<h2>五、按现象倒推的五个检查点</h2>
<p>不要从「可能被标记了」开始查，从现象倒推更快。五个检查点按成本从低到高排列。</p>
<h3>先查出口归属与类型</h3>
<p>成本最低，一次查询几分钟。归属不符是最常见也最容易忽略的原因，先排除这一项，能省掉后面大量猜测。</p>
<h3>再查会话与环境</h3>
<p>时区、语言、浏览器版本、DNS 解析路径，四项对齐后再看现象是否消失。很多所谓「出口被标记」，改完这四项就好了，与出口无关。</p>

<h2>常见问答</h2>
<h3>出口被标记了，换一个 IP 就能解决吗？</h3>
<p>答：如果是出口侧的整体降级，换出口通常有效；如果是账号侧关联或环境不一致，换出口只是把问题挪到新地址上，过几天还会出现。</p>
<h3>独享出口是不是就不会被标记？</h3>
<p>答：不保证。独享降低的是共享带来的干扰，不改变账号行为和环境一致性这两项。独享出口上跑异常高频的请求，一样会出问题。</p>
<h3>怎么判断是出口问题还是账号问题？</h3>
<p>答：做一次交叉验证。用同一账号换出口、用同一出口换账号，各试一次。换出口就好说明是出口侧，换账号就好说明是账号侧，两个都不好则是环境或平台侧。</p>
<h3>冷却期一定要七天吗？</h3>
<p>答：不必教条。三天是常见下限，七天更稳妥。资源紧张时可以缩短，但要相应降低新账号的使用强度，给一段适应期。</p>
